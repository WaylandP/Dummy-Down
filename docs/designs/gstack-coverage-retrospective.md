## Problem statement

Dummy-Down translates cybersecurity requirements into understandable teaching
material. Its README describes a source-bound, open-source learning resource,
starting with CMMC. The current homepage, three perspectives, glossary and focused
practice are implemented. The owner also wants to learn software development and
review incremental progress in a browser.

The immediate failure is workflow accountability: earlier delivery used selected
gstack guidance, but did not establish complete inventory, current-revision
execution coverage or consistent routing through all applicable stages. A skill
link, a read, a generic review and passing tests have different meanings. The
owner asks for “verifiable coverage,” not another application redesign or the
completion of the entire roadmap.

Doing nothing preserves a working application but leaves the same ambiguity for
the next contribution. Re-running everything indiscriminately would create paid,
authenticated or production side effects without improving this learning tool.
Repair the evidence and routing contract, then perform the missing authorized
reviews within their actual prerequisites.

## Recommended approach and acceptance criteria

1. Retain the healthy pin, runtime and licenses. Enumerate actual canonical
   templates and host rules rather than counting directory links. Repair only
   demonstrated project-scoped defects; preserve unfinished work and global
   settings. Fresh-environment checks exercise the existing bootstrap.
2. Publish one inventory and an early execution-gap checkpoint before long review.
   Installation/discovery status and execution status are separate fields. Every
   canonical name has a purpose, trigger, host mapping, prerequisites, important
   side effects and concrete current applicability.
3. Complete this retrospective office-hours specification and its real native
   spec review. Then use one autoplan sequence, CEO → Design if UI → DX if scope
   enables it → Eng last, recording underlying reviews once. The coordinator
   directs dispatch; no recursive reviewer tree or overlapping file ownership.
4. Run applicable missed local design, functional, developer, test-value,
   shared-code, performance, security-prerequisite, code and documentation stages.
   Choose QA or report-only QA as alternatives. Read installed instructions and
   actual lazy sections before execution; a generic review is never relabeled.
5. Record exact reviewed revisions or input fingerprints, helper receipts,
   commands/artifacts, material findings, fixes and unresolved limitations. Check
   old receipts for scope and staleness before reusing them. Only real command
   results populate execution status. Review completion is not native discovery.
6. Persist six practical routes: features, branding/UI, bugs, docs, compliance
   content, and release/post-deployment. Evaluate all skill triggers each task;
   a spelling correction need not run a product interview. User boundaries remain
   stronger than a skill's defaults, including safety and release utilities.
7. The structural checker rejects missing entries, duplicate canonical names,
   broken mappings and absent required records using small existing tooling.
   State explicitly that passing it does not prove execution, authenticity,
   review quality, human content approval or enforceable hooks. Keep gstack out
   of production app dependencies/build and do not silently add heavy CI tooling.
8. Limit root plus two workers, one correction after a failed command and at
   most two review/fix rounds per stage. Respect stricter stop conditions by
   reporting incomplete work instead of extending the loop. Publish resumable
   checkpoints containing completed/running/blocked/next/latest pushed revision.
9. Push validated independent slices on one open feature PR. Inspect CI and
   Vercel for that exact SHA, preserve protected-preview limits, and never merge.
